A collection of browser-based benchmarks comparing multithreaded WebAssembly, single-threaded WebAssembly and native JavaScript across compute-bound, memory-bound string-processing, etc workloads, run on 3 separate browsers.

WebAssembly threading works by loading the same WASM module into several Web Workers that share one linear memory buffer through a SharedArrayBuffer, synchronised with atomics and mutexes. It requires cross-origin isolation, which means the server must set the headers: 

	
	Cross-Origin-Opener-Policy
	Cross-Origin-Embedder-Policy

In Rust, the rayon crate abstracts the parallel execution, and wasm-bindgen-rayon bridges it to Web Workers.

Benchmarks

Six benchmarks cover different bottlenecks: constant-folded integer summation, matrix multiplication, Gaussian image blur, substring search, array sorting, and Pearson correlation. Between them they stress compute throughput, JS↔WASM copy costs, UTF-16 to UTF-8 transcoding, and thread coordination overhead.

Methodology

  • 100 warm-up runs are discarded, then 50 runs are recorded per input size per runtime.
  • Input data is regenerated fresh each run, and input sizes are tested in randomised order to reduce JIT and memory-state bias.
  • Outliers are removed with the 1.5×IQR rule before medians are computed per input size.
  • Results are aggregated across input sizes per browser and test, using median, coefficient of variation, and overhead relative to native JS.
  • Tested across Firefox, Chrome and Microsoft Edge, with results stored per browser in SQLite.

Key findings

  • Multithreaded WASM gives the largest speedups on embarrassingly parallel, compute-bound work: roughly 8× for matrix multiplication and 3.5× for image blur, versus native JS.
  • Single-threaded WASM matches or beats native JS on numerical workloads, thanks to LLVM's ahead-of-time optimisation.
  • WASM loses to native JS on string-heavy work like grep, due to the copy and UTF-16→UTF-8 transcoding cost at the JS↔WASM boundary.
  • Threading gives negligible or negative returns on memory bound or small input workloads, where coordination overhead outweighs the parallelism.
  • WASM execution is generally lower-variance than native JS, which matters in latency-sensitive contexts.

Prebuilt WASM modules are checked into the repo, so the benchmarks can be run without a Rust toolchain. To rebuild them from source, rust-toolchain.toml pins the Rust nightly compiler needed for the threading proposal, and cargo-make drives the build: 

cd rust
cargo make build-wasm   # compiles both singlethread and multithread crates

To run the benchmark suite itself:

npm install
node .             # starts the Express server

The page loads the JS, single-threaded WASM and multithreaded WASM implementations, spawns Web Workers via wasm-bindgen-rayon, and runs each benchmark across a range of input sizes, storing results in results.db for offline analysis and rendering them with Chart.js.
